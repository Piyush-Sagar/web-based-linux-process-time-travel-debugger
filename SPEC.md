# Web-Based Linux Process Time-Travel Debugger: v1 specification

## Requirements and decisions
Source: `C:/Users/sagar/Downloads/Web_Based_Linux_Process_Time_Travel_Debugger.pdf`, both pages. The PDF requires a C++ Linux ptrace engine, periodic checkpoints, actual restoration and forward replay, register/memory/signal/event capture, a React/TypeScript timeline, REST/WebSockets, and CMake. It specifies no executable ABI, syscall model, step definition, storage format, performance target, or isolation model.

V1 is a local educational debugger for bundled, small, single-threaded x86-64 C/C++ programs. No arbitrary uploaded executable or attachment to existing processes. Demos compile without libc, PIE, stack protector, or SIMD. `_start` is the entry point. Inline assembly only supplies Linux syscall wrappers. This restriction is necessary to make complete restoration achievable without reconstructing arbitrary kernel resources. It does not claim general Linux replay.

## Steps and state
Step 0 is the first genuine instruction stop, after one bootstrap instruction at `_start`. The synthetic exec stop on the tested kernel reports a reserved EFLAGS bit differently and cannot accept that bit via SETREGS; using a genuine stop makes architectural flags restorable without hiding differences. One subsequent step is one `PTRACE_SINGLESTEP` instruction, including one complete supported syscall. A faulting instruction produces a signal stop at its step; fatal signals can subsequently be delivered to capture termination. Pause occurs between instructions. Continue executes repeated bounded steps, allowing pause commands between batches. Bounds: 2,000 instructions, 256 KiB writable memory, 4 KiB per syscall payload, 8 sessions.

Each event contains general registers (hex strings, preserving 64-bit values), selected demo memory, instruction pointer, syscall number/arguments/result/output when applicable, signal, and execution status. Terminal exit events have no inspectable registers/memory. Checkpoints additionally capture every writable private mapping and x86 extended CPU state. Storage is versioned JSON with checkpoint bytes, immutable recorded events, executable identity, mapping layout, and input records. A build-time manifest checks demo identities on launch/load. Checksums detect accidental changes; this is not a cryptographic trust mechanism.

## Supported syscalls and rejection
`getrandom` and `clock_gettime` execute during recording; return values and output bytes are captured. `write` is limited to stdout/stderr, 4 KiB; output is captured in the trace and suppressed during replay. `exit` and `exit_group` terminate the trace. No reads from files or stdin in v1. Other syscalls are rejected before execution, including clone/fork, exec, mmap/brk, open, network, signal handlers, and ptrace. Asynchronous signals, nondeterministic CPU instructions, changing/shared mappings, vDSO calls, self-modifying code, and untrusted executables are unsupported. Approved demo images are hash checked; SIMD/x87 are outside the demo contract, although extended state is captured. Rejection ends forward recording explicitly and preserves the prior trace.

## Checkpoint restoration and replay
The child disables ASLR with `personality(ADDR_NO_RANDOMIZE)` before exec. Failure is a launch error. At periodic stopped instruction boundaries, capture all writable mappings, GPRs and extended CPU state. Restore by launching the identical approved executable with a fixed argv/environment, checking the mapping layout against the checkpoint, writing all checkpoint pages into the new live tracee, and setting extended state and GPRs. This reconstructs user state, not arbitrary kernel state. No tracee kernel resources are allowed beyond inherited stdout/stderr, and replay suppresses writes. A terminated original process can therefore be restored too.

Replay starts at the nearest checkpoint at or before the requested step. Ordinary instructions genuinely execute. For recorded input/output syscalls, replace the syscall number with an invalid number for one real syscall instruction, then inject only the recorded syscall result and output buffer and normalize `orig_rax`. Validate number, arguments, result payload bounds, all GPRs, and selected memory at every replayed stop. Do not copy ordinary recorded registers or memory to hide divergence. A mismatch aborts replay. Terminal fault stops can be reproduced; replay to an exited process is rejected as having no inspectable live state. Historical browsing never mutates execution and is labeled separately from live restored execution.

`getrandom` and time buffers are replayed from the log, independent of new host values. Writes have one original side effect and none during replay. Unsupported external side effects are refused. Snapshot bytes alone cannot restore sockets, files, threads, or signal-handler kernel state, explaining the scope boundary.

## Custom engine vs rr
A custom ptrace engine meets this narrow contract with instruction stepping, complete writable-memory checkpoints, fixed layouts, and syscall mediation. It is slow and unsuitable for general applications. rr is preferable for production-scale multithreaded Linux programs and broad syscall coverage. Adopting it would replace the custom replay engine and require an integration design. Its official requirements include supported CPUs and VM performance-counter virtualization: https://github.com/rr-debugger/rr . We retain the custom engine and test it on WSL2; rr availability alone will not be called a working alternative. ptrace reference: https://man7.org/linux/man-pages/man2/ptrace.2.html .

## Architecture and API
Deployment may be native x86-64 Ubuntu in VirtualBox or Ubuntu WSL2. Keep server and browser within the Ubuntu guest for the VirtualBox workflow, retaining loopback binding. Run preflight, backend replay tests and browser tests on each target guest before claiming verification; WSL results cannot establish VirtualBox correctness.

CMake builds demo binaries, an engine library, CLI, and a C++ Boost.Beast loopback HTTP/WebSocket server. A single worker owns all tracee operations because ptrace ownership is thread sensitive. REST requests are serialized on that worker. Continue progresses in short batches; WebSocket clients receive session updates with actual state. React uses these APIs exclusively. No mocks in the delivered UI.

`GET /api/demos`; `GET/POST /api/sessions`; `GET /api/sessions/:id`; `GET /api/sessions/:id/events`; `GET /api/sessions/:id/state?step=N` (history only); `POST /api/sessions/:id/control` with action step/continue/pause/terminate/restore and optional target step; `DELETE /api/sessions/:id`; `GET /api/health`; WebSocket `/ws`. Restore responds with live state and explicit verification status. Only loopback binding; reject cross-origin mutations. No authentication or remote hosting in v1.

## Acceptance
1. WSL2 build and ptrace launch/step/pause/continue/exit/crash tests pass.
2. Persisted traces contain GPRs, memory, supported syscalls, signals, and complete checkpoints; reopen in a new engine and restore.
3. Crash demo records SIGSEGV; inspect earlier historical steps, restore a prior checkpoint into a new PID, replay multiple selected targets, compare all GPRs and selected bytes to recording, then reproduce the crash. Test changed random/time inputs and suppress duplicate writes. Unsupported syscall rejected before effect; trace/executable corruption rejected.
4. API and browser tests drive real sessions through the same scenario. UI clearly distinguishes history from live replay and reports failures.
5. Exact setup and commands, bounded resources, limitations and evidence in README/STATUS.
